# 0007 — Runners execute inside tmux, terminals open on demand

**Status:** accepted

Every AI runner (`claude`, `codex`, `opencode`) ran headlessly (`HeadlessRunner`): piped stdio, one-shot, prompt baked into argv. The orchestrator only ever read the raw output to scan for a `<<<ORDEWELL_CHECKPOINT>>>` / `<<<ORDEWELL_DONE_...>>>` marker (`VerdictEngine`) and wrote back two fixed sentinel strings. `task_output` reached every client over the websocket but the TUI dropped it outright — a user could never see, let alone type into, what a runner was actually doing. The VS Code extension came closer (`VsCodeTerminalRunner` opens a real integrated-terminal PTY per runner) but Ordewell's own webview still never routed keystrokes into it.

The ask (issue #24 follow-up): every spawned runner should be a real, interactive terminal a user can open and type into directly — the tool's own UI, arrow keys, everything — while Ordewell keeps watching in the background and still auto-advances the dependency graph.

## Decision

Tasks run in a **tmux window** instead of a piped subprocess (`TmuxRunner`, alongside `HeadlessRunner`, both behind `ITerminalSession`/`ITerminalRunner`). The daemon owns **one shared tmux session per port** (`ordewell-<port>`), one window per task attempt. `ordewell tui` opens a **real OS terminal window** attached to a task's tmux window on demand (`t` in the plan pane, or `/terminal <id>`) — this works because the daemon is always local (`ensureDaemon` only ever binds `127.0.0.1`), so no new network protocol was needed to resolve the tmux target; the CLI computes it itself from `port` + `taskId`.

## Key properties

- **Drop-in, not a rewrite (T1).** `ITerminalSession`/`ITerminalRunner` already decouple `VerdictEngine` and `PoolAwareRunner` from the transport — `TmuxRunner` satisfies both with zero changes to orchestration. `VerdictEngine.flattenTerminalOutput` was already written to strip ANSI/box-drawing/whitespace from interactive-TUI output, so tmux's captured text needed no new parsing.
- **Byte-exact streaming, not polling-diff (T2).** Output is captured via `tmux pipe-pane` into a per-session log file, tailed by byte offset, rather than periodic `capture-pane` snapshots diffed by prefix-matching. A snapshot-diff heuristic can duplicate content on a scrollback resync (double-counting a checkpoint marker); a byte offset into an append-only file cannot.
- **Windows outlive the task, not the daemon (T3).** The command is wrapped so the window `exec`s into a login shell after reporting its exit code — a finished task's terminal stays open for inspection instead of vanishing. Windows are only closed by an explicit user cancel, a retry (which opens a fresh window rather than clobbering the failed attempt's output), or daemon shutdown.
- **One cleanup guarantee, not per-task bookkeeping (T4).** The single thing that must never leak is the shared tmux session itself. `main.ts`'s existing SIGINT/SIGTERM handlers call `TmuxRunner.killSession()`, which takes every window (and whatever's running in it) with it in one call. A crashed prior daemon's orphaned session on the same port is reaped by `ensureSession()` at the next startup — bounded to at most one stale session per port, never unbounded growth.
- **Automatic, not opt-in (T5).** `hasTmux()` gates the whole feature the same way `HeadlessRunner` already gates the `script`-PTY-wrap hack for `requiresTty` runners: silently on when the binary is present, silently falls back to today's exact `HeadlessRunner` behavior when it isn't. No new setting.
- **No new wire protocol (T6).** Opening a terminal is entirely client-local: `packages/core/src/utils/tmux.ts`'s naming helpers (`tmuxSessionName`, `tmuxWindowName`) are shared by the daemon (creates windows) and the CLI (attaches to them) purely by both computing the same deterministic names from `port`/plan-session/`taskId` — no HTTP endpoint exists for "does this task have a terminal."
- **Interactive shape, autonomous permissions (T8).** "Headless" was one flag doing two jobs: picking the CLI invocation shape (`codex exec` / `opencode run` vs the runner's TUI) *and* switching on the flags that stop the agent asking permission. A tmux window is both at once — a real TTY whose TUI is the entire point of this ADR, running unattended — so the two are separate axes in `ResolveContext` (`interactive`, `headless`), and the transport declares them independently. Getting this wrong is silent: the window opens, the task even succeeds, and the user just sees `codex exec` log lines where the TUI should be. Runners whose non-interactive subcommand implies permissions Ordewell then has to restate: `codex exec` neither asks for command approval nor asks whether the workspace directory is trusted, while the TUI asks for both by default and would sit on a menu no orchestrator can answer — hence `-a never` and a `projects.<cwd>.trust_level` override on the interactive shape only.
- **Windows are scoped by plan session, not just task (T7).** Task ids are only unique within one plan — every planner names its first task `task-1` — and finished plans' windows stay open (T3), so an unscoped name would collide with a previous plan's window on the *second plan a daemon ever runs* and pipe the new task's output into the old window. `PoolAwareRunner` therefore tags each spawn with its plan session id (`planSessionId`), which flows into the window name, the runner-session id, and the log file path; for the same reason, one plan's stop/stop-all only ever touches the sessions it spawned, even though the underlying `TmuxRunner` (and its tmux session) is shared by every plan in the pool.

## Considered options

- **A pty-multiplexer built into the TUI's own render loop (M2).** Rejected: the TUI's whole render model is pure `render(state) → string[]`, home-and-overwrite (ADR-0006); attaching a live runner needs raw ANSI passthrough, a fundamentally different mode. Doing this over the daemon's WebSocket (since a runner may not be spawned from the same process as any given TUI client) would also mean building bidirectional binary streaming plus resize propagation from scratch — reimplementing tmux, worse.
- **Capture-pane polling with prefix-diffing (M3).** Rejected in favor of `pipe-pane` + file tailing (T2): diffing periodic snapshots needs a resync heuristic whenever the pane's scrollback is exceeded between polls, which can re-emit already-seen content and double-count a checkpoint marker. `pipe-pane` gives an exact append-only byte stream tmux is already designed to produce.
- **Spawn a real OS terminal emulator as the *only* transport (M4, no tmux underneath).** Rejected: it would only work with a local GUI, failing silently on every SSH/headless box — which is a large fraction of where a terminal-based TUI actually runs. tmux underneath means the daemon-side execution and the checkpoint/verdict machinery keep working identically whether or not a GUI is ever attached; opening a terminal is a pure convenience on top, not a requirement for the pipeline to run.
