# 0003 — Per-runner model allowlist for the planner

## Problem

Ordewell's planner emits `assignedModel.modelId` per AI task drawn from `modelsByRunner`, the set `ModelResolver.modelsForRunners()` discovers per runner. There is no constraint on which of those ids the planner may pick — a user who only wants the planner to choose from `kimi-2.6` and `deepseek-v4-pro` on opencode has no way to express it; the planner sees the full discovered set and is free to pick the expensive `gpt-5`.

## Decision

We decided to add a per-**RunnerId** model-id allowlist (stored on `UserSettings.modelAllowlist: Partial<Record<RunnerId, string[]>>`, defaulting to unset = "all models fetched as available"). The allowlist **shapes what is written into the plan, not a runtime contract**: it narrows what `modelsByRunner` the planner sees in its prompt, and what a model written into a task meets is decided in one place, the assignment resolver (`resolveAssignment`), by who wrote it. Loaded plans keep their stored ids as-is, a model the user switched to with the runner's own `/model` is written regardless (ADR-0041), and the orchestrator (the executor) is never aware of the allowlist.

## Key properties

- **What is written, not what runs (P1).** The restriction shapes what a task is given when it is written, by whichever writer, and never what runs: a runtime guard in `TaskOrchestrator.startTask` was rejected, since it would turn advice into a hard contract and refuse a model the user switched to. Each writer's outcome for a model it names that the allowlist excludes is one row of the resolver's (`AssignmentWriter`):
  - a **submitted plan** has it replaced (B1), and the planner is told;
  - a **planner edit** is refused, which the planner answers in the same reply (ADR-0012);
  - a **user's edit** of a task's model is refused with the reason: the pickers list every discovered model, so the refusal is how the user learns the restriction;
  - a **task the user adds** has it replaced, and the user is told — never silently;
  - the **runner's own `/model`** is written as it is (ADR-0041).
  A model the writer did not touch stays even off the allowlist: the allowlist shapes what is written, not a model the user switched to (ADR-0043).
- **Replace stray ids (B1).** Where a model is replaced, or a missing one filled, it is the allowlist's first model the runner lists (the allowlist's order is the priority — the user controls it when picking), else the allowlist's first even unlisted (R1: the user named it), else the runner's first. Not pass-through (would let a plan silently ignore the restriction).
- **Carry the paired `thinkingEffort` to the nearest level (T2).** A replaced model takes the effort to the nearest level it offers, none where it offers none or discovery does not list it — the one rule every model change follows (`clampThinkingEffort`: a move, a `/model`, a surface's picker, a replacement). The id-keyed `model_id` list the allowlist stores (W1) intentionally excludes variant/eﬀort granularity — the variant pick on an *allowed* model is unconstrained.
- **Every task, said aloud, runner untouched (V1).** The resolver walks subtasks as well as tasks — a subtask runs as a task of its own — and returns what it changed beside the tasks, so `submit_plan` and `edit_plan` tell the planner which model or effort moved. It never moves a task to another runner: a runner the plan may not use is refused when the task is planned (`checkPlanInvariants`), never swapped for the first allowed one. The planner may use the runners enabled now, for a submitted plan and an edit alike (`assignableRunners`), checked as the change is submitted and again as it lands; a runner a task once ran on (`plan.runners`) records where work ran and does not let new work go there. So an edit naming a runner switched off since is refused, with the enabled runners listed, for a task or subtask it adds, a task it moves there (from another runner switched off too), a manual task it makes an AI one there, and a split part or merged task, which are new tasks, even one that would inherit the runner from the task it came from; a task it adds naming no runner lands on the first enabled one. A task the edit leaves on that runner stands as assigned, untouched or re-armed, and a model or mode it names for that task is still resolved against that runner's modes and allowlist. The user's own edits may name any runner. A model only *another* runner lists provably cannot run on the task's (R1), so it is treated as unassigned and refilled from the task's runner, and said: a planner edit that moves a task to another runner and names no model, a merge or split part placed on another runner, and a submitted task paired with another runner's model all land on the task's runner's model.
- **Two modules, split by concern (L3).** `ModelAllowlistResolver` owns the allowlist's reading and showing: the nudge (`filterModelsForPrompt`), the three-way reading (`effectiveAllowlist`) and the effort ladder. What a written task ends up with is the assignment resolver's (`TaskAssignment`), which every writer calls, so the outcomes cannot drift apart between paths. Neither lives in `PlanValidator` (which validates the plan's own invariants, unrelated) nor in `ModelResolver` (which owns discovery/routing; CONTEXT.md is explicit that the names differ by one letter on purpose — mixing concerns ﬁghts the established split).
- **Runner-level granularity (G1).** One allowlist per `RunnerId`, matching `modelsByRunner`'s shape. `runnerProvider` (the per-model backend distinction the UI surfaces) stays display-only — promoting it to an allowlist key would split one logical choice into two against the grain of the existing prompt/dropdown/coerce paths.
- **Discovery settles only what it can prove (R1).** Discovery can be stale, and a runner may list nothing, so "this runner didn't list it" does not make an allowlisted id wrong. `effectiveAllowlist` keeps an id the runner lists, keeps an id **no** runner lists (the user named it; the runner validates last), and drops an id listed only by *other* runners — it provably cannot run here. If that leaves nothing, the allowlist was about another runner and the restriction is off for this one. An allowlisted id discovery does not cover is synthesized into the prompt's list rather than falling back to the full discovered set, so a set allowlist stays a hard bound on what the planner sees. D1: both "unset" and "explicit empty array" mean "no restriction" — the user can't trap themselves in a "block all" state.
- **Read live on every turn (C1).** The catalog is re-sent every planner turn (`Session.catalogBlock`, and the `taskQuery` catalog answer, ADR-0012), and both read the allowlist and the resolver's discovery cache live (`ModelResolver.getCachedRunnerModels`, which never triggers discovery; the Session discovers on its own only where nothing is cached). Only the system prompt's model block is a snapshot from `startPlanning`, and the per-turn block supersedes it. A change to the allowlist reaches the running conversation on its next turn.
- **A refusal reads it the same way.** The resolver accepts an id in the runner's effective allowlist even when discovery never listed it, for every writer.
- **Every emit-path ﬁlters and resolves; `loadPlan` untouched (E1).** `generate`, `startPlanning` and `continueConversation` each build a `modelsByRunner` block and yield fresh task arrays — all need the ﬁlter (otherwise the restriction leaks) and the resolver's landing pass (`resolveAssignments`, otherwise stray ids land unrewritten). `loadPlan` only restores a previously-saved plan; resolving there would silently rewrite the user's own previously-edited assignments on reload, defeating P1.

## Considered options

- **Hard contract, dropdown also ﬁltered (P2).** Once a runner is restricted to `{A, B}`, nothing — planner or human — can assign `C` on that runner, and no task holds it. Rejected: the restriction would reach what runs — a model the user switched to with the runner's own `/model`, or one a saved task already holds, would be undone — and a filtered picker hides what exists instead of saying why a pick is refused.
- **Auto-coerce to manifest `fallbackModels[0]` (B2).** Rejected: `fallbackModels`'s documented meaning is "when discovery yields nothing," not "preferred coercion target"; overloading it is a surprising semantic stretch the next reader would question.
- **Coerce to orchestrator model (B3).** Rejected: the orchestrator model is a planning model (OpenRouter/Gemini id), not a runner executor model — its id may not even be in the runner's discovered set, and using it would cross a domain boundary.
- **Coercion in `PlanValidator` (L1).** Rejected: that module validates the plan's own invariants (ids, dependency integrity, runners, slices); model-id membership is an unrelated concern and would grow an unrelated new param branch.
- **Swap a task on a runner outside the allowed set to the first allowed runner.** It was the coerce's first step at first. Rejected: it rewrote a choice the planner made without a refusal it could answer, against ADR-0001's rule that the plan is what runs, and since subtasks were not checked it let a runner nobody enabled into the plan's runner set.
- **Coerce top-level tasks only.** It was so at first. Rejected: subtasks run as tasks of their own, so a subtask's model skipped the allowlist and its effort was never clamped.
- **Coercion in `ModelResolver` (L2).** Rejected: CONTEXT.md's ModelResolver entry is explicit ("the names differ by one letter on purpose") — mode coercion lives in `ModeResolver` precisely *because* it didn't belong in `ModelResolver`. Mixing the new policy into the discovery/routing module repeats the mistake the codebase already corrected.
- **Allowlist authoritative for every id (R2).** Rejected: an id listed only by another runner provably cannot run on this one; keeping it hands the planner a model that fails once a task is already running.
- **Discovery authoritative: drop every id discovery does not list, and turn the restriction off when nothing is left.** It was R1 at first. Rejected: discovery can be stale and a runner may list nothing, so a deliberate pick was silently dropped — and an emptied list fell back to the full discovered set, showing the planner exactly the models the user had excluded.
- **Discovery authoritative + warning (R3).** Rejected: a new warning channel for an edge case the three-way reading above already settles.
- **Empty array = block-all (D2).** Rejected: an error state with no graceful recovery — hard to distinguish "user wants to block all" from "default state, never conﬁgured," and contradicts the spec wording "all models fetched as available by default."
- **Runner+Provider-level allowlist (G2).** Rejected: divergence from the runner-keyed `modelsByRunner` / dropdown / prompt-block shape. Coercion's "ﬁrst allowed" would need provider-aware logic and a `ProviderRouting` call into the coerce path — concern creep.
- **Model+variant allowlist (W2).** Rejected: the dropdown is id-keyed; a variant restriction would silently not apply to manual overrides, the pick list doubles or triples, and the paired-eﬀort control is unmotivated by the user's actual ask ("select … only the ones that the planner model will use"). Variant control is a clean *future* corollary on top of the id-keyed allowlist, not a refactor.
- **Leave `thinkingEffort` on coercion (T1).** Rejected: we'd be *introducing* an unsupported id+eﬀort pairing as a side eﬀect of our own rewrite, worse than the inherited (unvalidated) state today.
- **Wipe the paired `thinkingEffort` on coercion.** It was T2 at first, because the effort was calibrated to a model the planner did not get. Dropped: a move, a `/model` and the surfaces' pickers each carried an effort differently, and the allowlist was the one place it was always lost; the nearest level keeps the intent without inventing a level the model lacks.
- **Silently replace a model the user adds a task with.** It was so at first, by narrowing the runner's catalog to the allowlist before deriving. Dropped: a replacement nobody is told of is a plan that differs from what its writer wrote (ADR-0001).
- **Keep a moved task's model when no allowlist is set.** It was the planner edit's behaviour, while a user's move re-derived it. Dropped: the task landed on a runner with a model it cannot spawn, and the planner was told nothing.
- **Coerce `thinkingEffort` to `allowlist[0]`'s ﬁrst variant (T3).** Rejected: "ﬁrst variant" is a covert priority for an eﬀort the planner picked deliberately; could silently pick `xhigh` for a task the planner wanted `low` on.
- **Snapshot at `startPlanning` (C2).** It was C1 at first: changes took effect on the next conversation. Rejected once the catalog went per-turn (ADR-0012): a snapshot kept a newly allowed model out of reach, and clearing the allowlist (which unsets the whole map) fell back to the restriction read at the start.
- **Rewrite the system prompt's model block mid-conversation.** Rejected: mutating API message history risks incoherent emissions where the model's prior tool calls referenced the larger set. A fresh per-turn block adds rather than rewrites.
- **Surface a restart warning (C3).** Rejected: observability that buys little, and moot once the catalog is read every turn.
- **Only a planner tool for listing models.** Rejected: API planners still need
  the per-turn catalog block. Coding-agent planners use `list_models` through
  the injected MCP server (ADR-0022); built-in manifests own discovery and
  mode settings, without terminal-only invocation fields.
- **Coerce on `loadPlan` (E2).** Rejected: would silently rewrite the user's previously-edited assignments the moment they reload a workspace — surprising, invisible, possibly destructive.
- **Filter only `generate`/`startPlanning` (E3).** Rejected: the conversation re-emits task arrays with a fresh `modelsByRunner` block — skipping the ﬁlter there leaks the full discovered set back into the planner's view, defeating the feature.
- **Runtime enforcement in orchestrator (X2/X3).** Rejected: the orchestrator is documented as a pure scheduler (CONTEXT.md); a guard there would refuse a manual-dropdown override that P1 explicitly allows, contradicting the design.

## Consequences

- `UserSettings` has a nested, non-boolean ﬁeld (`modelAllowlist?: Partial<Record<RunnerId, string[]>>`); `SettingsService.load`/`persist` and `OrchestratorPool.updateSettings` handle that shape. The in-memory settings cache stays (S1-cache) — cross-process staleness is the documented, pre-existing trade-oﬀ shared by every setting.
- `ModelAllowlistResolver` sits next to `ModeResolver`: `ﬁlterModelsForPrompt(modelsByRunner, runners)`, `effectiveAllowlist` and `clampThinkingEffort`, pure functions, injected allowlist. The nudge is called by every emit-path before building the prompt block. `TaskAssignment.resolveAssignment` is called by every writer as it writes, and `resolveAssignments(tasks, planned, catalog) → { tasks, adjustments }` runs on every freshly-emitted task array before the tasks land on the plan.
- `Planner` / `AiService` / `Session` threads the resolver through `PlanRequest` and `IAiService.startConversation`'s `modelsByRunner`. `loadPlan` and `TaskOrchestrator.startTask` are unchanged.
- VS Code has an `ordewell.conﬁgureModelAllowlist` command (QuickPick runner → `withProgress` discover → `showQuickPick({ canPickMany: true })` over that runner's discovered models, pre-checked with the current allowlist; empty discovery aborts with a message). The per-task dropdown in `PlanCardGroup.tsx` is unchanged.
- The CLI has `ordewell allowlist` (`set <runner> <id1,id2,…>` / `clear <runner>` / `show`), calling the existing `PATCH /settings` route. No new TTY picker dependency.
- The daemon's `PATCH /settings` route is the single persistence channel both surfaces call — no new entry in the daemon route table (`DAEMON_ROUTES`), since the allowlist is a setting, not a toggle action.
- A future reader sees `ModelAllowlistResolver` separate from `ModelResolver`, `UserSettings.modelAllowlist` keyed by `RunnerId` not by `runnerProvider`, `loadPlan` untouched, and the orchestrator unaware — this ADR is the "why."
